= Module 01: Getting Started
:navtitle: Module 01: Getting Started

In this module you will learn what *External metering: per-user token usage and
cost* does, observe the MaaS environment it meters in your workshop cluster,
and walk the metering data path end to end.

**Learning objectives:**

* Explain the role of the external-metering IPP plugin and the standalone metering service in RHOAI 3.5
* Verify that the MaaS custom resources that external metering depends on are present in the cluster
* Describe how a request's token usage becomes a cost-attributed metering event

ifeval::["{feature_maturity}" == "DP"]
NOTE: External metering for per-user token usage and cost tracking is a

Red Hat in any way, might not have any documentation, are subject to change or
removal at any time, and have received limited testing. In RHOAI 3.5 the
feature is described in the release notes; step-by-step installation and
configuration procedures for the plugin and the metering service are not yet
part of the product documentation.

== Exercise 1: Observe the MaaS environment that external metering meters

The external-metering plugin meters inference requests that pass through the
AI Inference Gateway — the MaaS gateway. Before looking at metering itself,
observe the MaaS foundations in your cluster.

. Confirm that the OpenShift AI Operator has deployed the DataScienceCluster
  and that the MaaS-related components are in place:
+

[source,bash,role="execute",subs="attributes"]
----
oc get datasciencecluster -n redhat-ods-operator
----

Expect one DataScienceCluster entry, typically `default-dsc`, with an `AGE`
value. This is the CR that the RHOAI operator reconciles to deploy MaaS.

. Verify that the Models-as-a-Service custom resource definitions (CRDs) are
  installed:
+

[source,bash,role="execute",subs="attributes"]
----
oc get crd | grep -E 'maas.opendatahub.io|aitenants'
----

Expect output that includes the following CRDs:

----
aitenants.maas.opendatahub.io
maasauthpolicies.maas.opendatahub.io
maasmodelrefs.maas.opendatahub.io
maassubscriptions.maas.opendatahub.io
maastenantconfigs.maas.opendatahub.io
tenants.maas.opendatahub.io
----

. Verify that the Tenant custom resource exists and is reconciled in the
  models-as-a-service namespace:
+

[source,bash,role="execute",subs="attributes"]
----
oc get tenants.maas.opendatahub.io -n models-as-a-service
----

Expect at least one Tenant resource with a `READY` value of `True` and a
reason of `Reconciled`, for example:

----
NAME             READY   REASON       AGE
default-tenant   True    Reconciled   5m
----

=== Verify

You have confirmed that the DataScienceCluster, the MaaS CRDs, and a reconciled
Tenant resource are present — the MaaS foundation whose inference traffic the
external-metering plugin meters.

With the foundation observed, the next step is to understand how a request
becomes a metering event.

== Exercise 2: Walk the external metering data path

This is a guided walkthrough — no commands. Follow the life of one inference
request and note where metering happens.

. *Request enters the AI Inference Gateway.* The external-metering plugin
  operates in the IPP plugin chain of the gateway. Before a request is
  processed, the plugin checks the user's balance from the metering service so
  that exhausted credit can stop the next request.

. *Usage is extracted from the provider response.* After the response returns,
  the plugin extracts token usage details from OpenAI and Anthropic provider
  responses. The plugin distinguishes five token dimensions:

[cols="1,2",options="header"]
|===
|Token dimension |What it captures

|Input tokens
|Tokens in the prompt sent to the model

|Output tokens
|Tokens generated by the model in the response

|Cached tokens
|Prompt tokens served from an existing cache

|Cache write tokens
|Prompt tokens written into the cache for later reuse

|Reasoning tokens
|Tokens consumed by reasoning-capable models before the final answer
|===

. *A CloudEvent is emitted.* The plugin emits the usage details as a
  CloudEvent to a standalone metering service backed by PostgreSQL.

. *The metering service aggregates.* The service aggregates usage, calculates
  cache-aware pricing — cached and cache-write tokens are priced differently
  from fresh input tokens — and stores the result for reporting.

. *Operators consume the data.* The service exposes an administrative
  dashboard and a REST API for usage queries and balance checks. Platform
  operators use them to track per-user and per-model consumption, attribute
  costs, enforce quotas, and generate chargeback reports.

=== Verify

You can describe, without referring back, the five stages of the data path:
balance check at the plugin, usage extraction from the provider response,
CloudEvent emission, aggregation with cache-aware pricing in the PostgreSQL
service, and consumption through the dashboard and REST API.

== Module summary

**What you accomplished:**

* Verified that the DataScienceCluster, MaaS CRDs, and Tenant resources are present in your cluster
* Walked the external metering data path from balance check to chargeback report
* Identified the five token dimensions the plugin extracts from OpenAI and Anthropic responses

**Key takeaways:**

* The external-metering plugin meters AI Inference Gateway traffic in the IPP plugin chain, checking balances before requests are processed
* CloudEvents carry per-request token usage to a PostgreSQL-backed metering service that aggregates usage and calculates cache-aware pricing
* The metering service exposes an administrative dashboard and REST API for usage queries and balance checks
