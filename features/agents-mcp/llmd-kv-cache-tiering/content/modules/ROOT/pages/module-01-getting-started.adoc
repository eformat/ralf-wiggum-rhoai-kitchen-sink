= Module 01: Getting Started
:navtitle: Module 01: Getting Started

In this module you will get a guided tour of Hierarchical KV Cache Tiering (llm-d) in
your workshop cluster: what the feature does, how the llm-d serving stack makes
KV cache reuse possible, and how to confirm your environment is ready for it.

**Learning objectives:**

* Explain what hierarchical KV cache tiering does for GPU inference workloads
* Describe how the llm-d Endpoint Picker schedules requests for KV cache reuse
* Inspect your cluster to confirm Distributed Inference with llm-d is available

== Exercise 1: Understand hierarchical KV cache tiering

Transformer-based large language models (LLMs) compute a *key-value (KV) cache*
during the prefill phase: the intermediate attention state for every prompt token.
The decode phase then reuses that state one token at a time. When a new prompt
shares a prefix with a previously seen prompt — a follow-up turn in a chat, a
repeated system prompt, or a long document used as context — the model can reuse
the cached state instead of recomputing it. Cache reuse is what makes multi-turn
and long-context workloads efficient.

*Hierarchical KV cache tiering* for GPU inference workloads takes this further.
It allows platform operators to serve more concurrent users on the same GPU
footprint, directly improving the cost-effectiveness of inference deployments.
Cache entries are automatically placed on the tiers operators configure, which
increases the effective cache size and the prefix-cache reuse rate across the
inference pool. Operators configure the tiers; placement happens automatically
at runtime — you do not tag or route individual cache entries.

In Red Hat OpenShift AI 3.5 this capability is a *Developer Preview* feature and
works together with *Distributed Inference with llm-d*, the serving stack that
provides the routing layer where cache-aware decisions are made.

== Exercise 2: Where the feature fits in the llm-d serving stack

The Endpoint Picker (EPP) is the request orchestration component of Distributed
Inference with llm-d. It sits between the Inference Gateway and the backend model
servers and processes every request through two layers:

* *Flow Control layer* — decides *when* requests are dispatched: priority-based
  queuing, saturation detection (queue depth and KV cache utilization), and load
  shedding to protect the inference pool.
* *Scheduling layer* — decides *where* each request is routed among the available
  model replicas using scorer plugins.

If you do not specify custom scheduler configuration, the system uses an
optimized default profile that combines four scorer plugins with weights
2:2:3:2:

[cols="2,1,3",options="header"]
|===
|Scorer |Default weight |What it optimizes

|`queue-scorer`
|2
|Routes requests to replicas with shorter queues to distribute load evenly

|`kv-cache-utilization-scorer`
|2
|Routes requests to replicas with more available KV cache capacity, preventing cache eviction

|`prefix-cache-scorer`
|3
|Routes requests with similar prompt prefixes to the same replica for cache reuse

|`no-hit-lru-scorer`
|2
|Least-recently-used tiebreaker that distributes new prompt patterns when no cache hit is found
|===

This default profile prioritizes KV cache reuse while maintaining balanced load
distribution. The prefix-cache-scorer uses hash-based cache hit detection, which
works in disconnected environments. For workloads with subtle prompt variations
and network access, an optional `precise-prefix-cache-scorer` upgrade uses
token-level matching, at the cost of a Tokenizer sidecar that downloads tokenizer
models during pod startup.

== Exercise 3: Confirm your environment is ready

Hierarchical KV Cache Tiering and its cache-aware routing ride on the llm-d
serving stack, so first confirm the stack is present in your working project.

. Confirm that `LLMInferenceService` resources are recognized by the cluster
and list any deployed models:
+
[source,bash,role="execute",subs="attributes"]
----
oc get llmisvc -n {guid}-{user}
----
+
Expected output shows either a list of deployed models with their URL and
`READY` status, or `No resources found` if you have not deployed a model yet.
Both are fine for this guided tour.

. List the `LLMInferenceServiceConfig` templates that back the llm-d topology
and router options in the deployment wizard:
+
[source,bash,role="execute",subs="attributes"]
----
oc get llminferenceserviceconfig -A
----
+
Expected output lists configurations such as topology presets and, if your
administrator created them, router configs whose names often contain `router`.
Note the namespaces they live in.

. Open the RHOAI dashboard, navigate to *Data Science Projects*, select your
project, and click *Deploy model*. In the wizard, expand *Advanced routing* and
observe that a *Default optimized routing* option is pre-selected — that default
is the 4-scorer profile you read about above.

[TIP]
====
If `oc get llmisvc` fails with `the server doesn't have a resource type`, the
Distributed Inference with llm-d component is not enabled in your cluster. Ask
your workshop facilitator before continuing.
====
