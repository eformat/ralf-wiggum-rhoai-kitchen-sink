= Module 01: Getting Started
:navtitle: Module 01: Getting Started

In this module you will act as the cluster administrator: enable the
`mcplifecycleoperator` component in the `DataScienceCluster` custom resource (CR),
turn on the `mcpCatalog` dashboard feature flag, and verify the operator pod is
running. You then switch to the developer hat, browse the AI Hub MCP Catalog in
the dashboard, and deploy an MCP server from a catalog entry into your working
project.

**Learning objectives:**

* Explain what the MCP Lifecycle Operator manages and how it powers the AI Hub MCP Catalog
* Enable the `mcplifecycleoperator` component by patching the `DataScienceCluster` CR
* Enable the MCP Catalog UI by patching the `OdhDashboardConfig` CR
* Deploy an MCP server from a catalog entry and validate every step from the CLI and the console

ifeval::["{feature_maturity}" == "TP"]
NOTE: This feature is a *Technology Preview*. The `mcplifecycleoperator`
component defaults to `Removed` in the `DataScienceCluster` for RHOAI
{rhoai_version}, so the operator is not running on a fresh installation — you
must enable it explicitly.
endif::[]

== Exercise 1: Enable the MCP Lifecycle Operator

The MCP Lifecycle Operator is managed by the Red Hat OpenShift AI Operator
through the `DataScienceCluster` CR, using the same component controller pattern
as other optional components such as `MLflowOperator` and `FeastOperator`. You
enable it by setting the `managementState` field of the `mcplifecycleoperator`
component to `Managed`.

. Identify the name of your `DataScienceCluster` object:

[source,bash,role="execute",subs="attributes"]
----
oc get datasciencecluster
----

. Enable the MCP Lifecycle Operator by patching the `DataScienceCluster`
  object. Replace `default-dsc` with the name from the previous step if
  different:

[source,bash,role="execute",subs="attributes"]
----
oc patch datasciencecluster default-dsc --type=merge \
  -p '{"spec":{"components":{"mcplifecycleoperator":{"managementState":"Managed"}}}}'
----

The component path mirrors the CR structure — this patch is equivalent to
setting the following in the `DataScienceCluster` CR:

[source,yaml,subs="attributes,callouts"]
----
spec:
  components:
    mcplifecycleoperator: <1>
      managementState: Managed <2>
----

<1> **Component:** the `mcplifecycleoperator` component in the `DataScienceCluster` CR, managed by the OpenShift AI operator.
<2> **Management state:** `Managed` installs and runs the operator; the default for this component in RHOAI {rhoai_version} is `Removed`.

NOTE: You can also enable the MCP Lifecycle Operator by using the OpenShift web
console, as described in *Installing and uninstalling OpenShift AI* in the RHOAI
documentation.

. Enable the MCP lifecycle feature in the dashboard by patching the
  `OdhDashboardConfig` custom resource. This is what makes the AI Hub MCP
  Catalog UI visible to developers:

[source,bash,role="execute",subs="attributes"]
----
oc patch odhdashboardconfig odh-dashboard-config -n redhat-ods-applications \
  --type=merge -p '{"spec":{"dashboardConfig":{"mcpCatalog":true}}}'
----

=== Verify

Confirm that the MCP Lifecycle Operator pod is running:

[source,bash,role="execute",subs="attributes"]
----
oc get pods -n redhat-ods-applications -l app.kubernetes.io/name=mcp-lifecycle-operator
----

Expect at least one pod in `Running` status, for example:

----
NAME                                          READY   STATUS    RESTARTS   AGE
mcp-lifecycle-operator-<id>                   1/1     Running   0          2m
----

Confirm that the `mcplifecycleoperator` component is reported as installed in
the `DataScienceCluster` status:

[source,bash,role="execute",subs="attributes"]
----
oc get datasciencecluster default-dsc \
  -o jsonpath='{.status.installedComponents.mcplifecycleoperator}'
----

The expected output is `true`. Then confirm the dashboard flag took effect:

[source,bash,role="execute",subs="attributes"]
----
oc get odhdashboardconfig odh-dashboard-config -n redhat-ods-applications \
  -o jsonpath='{.spec.dashboardConfig.mcpCatalog}'
----

The expected output is `true`. In the OpenShift console at
{openshift_console_url}, log in and confirm the *AI hub* → *MCP servers* entry
appears in the dashboard navigation.

TIP: If the operator pod is not running, check the OpenShift AI operator logs
and confirm the patch succeeded with `oc get datasciencecluster default-dsc -o
yaml | grep -A2 mcplifecycleoperator`.

With the operator enabled, the next step is to browse the catalog and deploy
your first MCP server.

== Exercise 2: Browse the AI Hub MCP Catalog

The AI Hub MCP Catalog provides the discovery and deployment interface for MCP
servers. The catalog UI is a federated plugin in the OpenShift AI dashboard and
is pre-loaded with MCP servers from Red Hat, technology partners, and the open
source community. A separate model-metadata-collection data container provides
the catalog metadata for MCP server discovery.

. In the Red Hat OpenShift AI dashboard, navigate to *AI hub* → *MCP servers*.
. Browse the available MCP servers. Each server card displays the server name,
  a description, supported tools, and the support tier. The support tiers are:

[cols="1,3",options="header"]
|===
|Support tier
|Description

|*Red Hat*
|Fully supported by Red Hat.

|*Partner*
|Supported by the technology partner who maintains the server.

|*Community*
|Best-effort support from the open source community.
|===

. Filter the catalog by deployment mode or supported transport protocols to
  find the server that meets your requirements. For the smoothest start, pick a
  server labeled with the *Red Hat* support tier.
. Click the MCP server you want to deploy to open its details page. Review the
  server metadata, including the list of tools it exposes, supported
  capabilities, and whether the server requires a service account.

TIP: The support tier tells you who backs the server *before* you deploy: Red
Hat servers carry Red Hat support commitments, Partner servers are supported by
the ISV, and Community entries have no official support commitment.

Now that you have browsed the catalog and chosen a server, you will deploy it
into your working project.

== Exercise 3: Deploy an MCP server from a catalog entry

Deploying from the catalog requires no Kubernetes manifests or manual container
image sourcing — the catalog UI generates the deployment, and the MCP Lifecycle
Operator creates the `MCPServer` custom resource (CR) in your namespace and
provisions the required `Deployment` and `Service`.

IMPORTANT: The *Deploy MCP server* button stays disabled if the MCP Lifecycle
Operator is not enabled on the cluster. Recheck Exercise 1 if the button is
greyed out.

. Click *Deploy MCP server* on the details page from Exercise 2.
. In the deployment dialog, review the YAML configuration field. If the MCP
  server requires a service account, set the `serviceAccountName` field under
  `runtime:` and `security:`:

[source,yaml,subs="attributes,callouts"]
----
spec:
  runtime: <1>
    security:
      serviceAccountName: <service_account_name> <2>
----

<1> **Runtime section:** the runtime configuration of the server presented in the deployment dialog.
<2> **Service account:** the name of the `ServiceAccount` resource that exists in your namespace.

You can omit the `serviceAccountName` field when the server needs no service
account, as with most catalog entries.

. Confirm the deployment by clicking *Deploy* in the dialog. The MCP Catalog
  submits the deployment request to the MCP Lifecycle Operator, which creates
  an `MCPServer` CR in your namespace and provisions the required `Deployment`
  and `Service`.

=== Verify

Confirm that the `MCPServer` custom resource shows a `READY` status of `True`:

[source,bash,role="execute",subs="attributes"]
----
oc get mcpservers -n {guid}-{user}
----

Expect the MCP server with `READY` status `True` and `ACCEPTED` `True`, for
example:

----
NAME              READY   ACCEPTED   IMAGE   PORT   ADDRESS   AGE
my-mcp-server     True    True       ...     ...    ...       2m
----

In the Red Hat OpenShift AI dashboard, navigate to *AI hub* → *MCP servers* and
verify that the MCP server is displayed on the *Deployments* tab.

NOTE: The `MCPServer` CR API version in this release is `v1alpha1`. Red Hat
makes no backwards compatibility commitment for this release, and CRD types and
fields can change in a future release without a migration path.

== Module summary

**What you accomplished:**

* Enabled the `mcplifecycleoperator` component in the `DataScienceCluster` and the `mcpCatalog` dashboard feature flag
* Verified the operator pod and component state from the CLI
* Browsed the AI Hub MCP Catalog and deployed an MCP server from a catalog entry

**Key takeaways:**

* The `mcplifecycleoperator` component defaults to `Removed` — MCP server deployment is unavailable until you set `managementState: Managed`
* The `mcpCatalog` flag in `OdhDashboardConfig` gates the catalog UI; without it, developers never see *AI hub* → *MCP servers*
* The catalog's *Deploy MCP server* action requires the operator: it creates the `MCPServer` CR and provisions the `Deployment` and `Service`

**Next steps:**

Continue to Module 02 to inspect the `MCPServer` custom resource the operator
created and manage the full server lifecycle: health, scaling, upgrades, and
removal.
