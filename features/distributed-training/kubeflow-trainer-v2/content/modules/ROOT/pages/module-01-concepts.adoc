= Module 01: Core Concepts
:navtitle: Module 01: Core Concepts

In this module you will understand what Kubeflow Trainer v2 is, the problems it
solves, and how its `TrainJob` and `ClusterTrainingRuntime` resources fit into
Red Hat OpenShift AI 3.5.

**Learning objectives:**

* Explain the role of Kubeflow Trainer v2 in RHOAI and how it replaces Training Operator v1
* Describe how `runtimeRef` connects a `TrainJob` to a `ClusterTrainingRuntime`
* Locate and inspect the pre-built training runtimes in your cluster

== Exercise 1: Where Kubeflow Trainer v2 fits

Kubeflow Trainer v2 is a single API for distributed training on OpenShift AI.
Instead of creating framework-specific CRDs such as `PyTorchJob` — where you had
to specify the full pod specification, environment variables, and distributed
training setup for every job — you create one `TrainJob` resource that
references a `ClusterTrainingRuntime` through the `runtimeRef` field. The
runtime handles the complexity of configuring `torchrun`, environment variables
(`MASTER_ADDR`, `MASTER_PORT`), node coordination, and container image defaults,
so you can focus on your training code and resource requirements.

[cols="2,3"]
|===
|Training Operator v1 (`PyTorchJob`) |Kubeflow Trainer v2 (`TrainJob`)

|Separate Master and Worker replica specifications
|A single `numNodes` field: a v1 job with 1 Master and 2 Workers is equivalent to `numNodes: 3`

|Per-replica resource configuration for Master and each Worker
|`resourcesPerNode` applies the same requests and limits to every training node

|Full pod spec, environment variables, and distributed setup per job
|Provided by the referenced `ClusterTrainingRuntime`, overridable per job via `podTemplateOverrides`
|===

RHOAI 3.5 ships these pre-built `ClusterTrainingRuntime` resources:

[cols="2,3"]
|===
|Runtime |Description

|`torch-distributed`
|General-purpose PyTorch distributed training with CUDA support

|`torch-distributed-rocm`
|PyTorch distributed training for AMD ROCm GPUs

|`torch-distributed-cuda128-torch29-py312`
|PyTorch 2.9 with CUDA 12.8, Python 3.12

|`training-hub`
|Training Hub runtime with built-in fine-tuning algorithms (OSFT, SFT)

|`training-hub-th05-cuda128-torch29-py312`
|Training Hub runtime with CUDA 12.8, PyTorch 2.9, Python 3.12
|===

You interact with Kubeflow Trainer v2 from three places:

* The OpenShift CLI (`oc`) and the Kubeflow Python SDK, for creating and managing `TrainJob` resources
* The OpenShift console, Administrator perspective: *Home → Search* to find `TrainJob` resources and *Workloads → Pods* for training pods
* The OpenShift AI dashboard, *Model training*, for real-time progress metrics when progress tracking is enabled

WARNING: In RHOAI 3.5, Kubeflow Trainer v2 is not compatible with Red Hat Build
of Kueue (RHBoK) 1.4 or later. Kubeflow Trainer v2 continues to function, but
the integration between Kubeflow Trainer v2 and Kueue does not. If your cluster
uses Kueue, keep RHBoK at version 1.3 or earlier and do not upgrade.

=== Verify

In the OpenShift console, switch to the Administrator perspective, click *Home →
Search*, select your project, type `TrainJob` in the Resources search field, and
confirm the `TrainJob` resource type is offered. This confirms the Kubeflow
Trainer v2 CRDs are installed on your cluster.

Now that you have confirmed the TrainJob resource type in the console, you will
inspect the pre-built runtime resources in your cluster.

== Exercise 2: Inspect the pre-built training runtimes

List the `ClusterTrainingRuntime` resources the platform administrator provisioned:

[source,bash,role="execute",subs="attributes"]
----
oc get clustertrainingruntime
----

.Example output
----
NAME                                          AGE
torch-distributed                             5m
torch-distributed-rocm                        5m
torch-distributed-th03-cuda128-torch28-py312  5m
training-hub                                  5m
training-hub03-cuda128-torch28-py312          5m
----

NOTE: The exact runtime names on your cluster can vary with the RHOAI release.
What matters is that at least `torch-distributed` and `training-hub` are present.

View the details of the general-purpose PyTorch runtime:

[source,bash,role="execute",subs="attributes"]
----
oc get clustertrainingruntime torch-distributed -o yaml
----

The structure of the `torch-distributed` runtime looks like this:

[source,yaml]
----
apiVersion: trainer.kubeflow.org/v1alpha1
kind: ClusterTrainingRuntime
metadata:
  name: torch-distributed <1>
spec:
  mlPolicy:
    torch:
      numProcPerNode: auto <2>
  template:
    spec:
      replicatedJobs:
      - name: Node
        template:
          spec:
            template:
              spec:
                containers:
                - name: trainer
                  env:
                  - name: MASTER_ADDR
                    value: "$(JOB_NAME)-node-0-0.$(JOB_NAME)" <3>
                  - name: MASTER_PORT
                    value: "29500"
                  command:
                  - torchrun <4>
----
<1> **`torch-distributed`** — a cluster-scoped runtime, available to every project.
<2> **`numProcPerNode: auto`** — the PyTorch distributed policy; `auto` matches the number of GPUs on each node.
<3> **`MASTER_ADDR` / `MASTER_PORT`** — node coordination, injected automatically so your training code does not set it.
<4> **`torchrun`** — the launcher that starts the distributed PyTorch process group.

NOTE: You do not need to create the `torch-distributed` runtime. It is provided
out of the box when the platform administrator enables the Kubeflow Trainer
component in the DataScienceCluster. Only the platform administrator creates or
modifies `ClusterTrainingRuntime` resources — as a data scientist you reference
them from your `TrainJob` (or create namespace-scoped `TrainingRuntime`
resources, covered in Module 03).

=== Verify

The `oc get clustertrainingruntime` command listed `torch-distributed` and
`training-hub`, and the `oc get clustertrainingruntime torch-distributed -o
yaml` command returned the runtime YAML including the `mlPolicy` and `template`
sections.

== Module summary

**What you accomplished:**

* Mapped Training Operator v1 concepts (PyTorchJob, Master/Worker replicas) to the TrainJob v2 API
* Located the Kubeflow Trainer v2 resources in the OpenShift console
* Listed and inspected the pre-built ClusterTrainingRuntimes in your cluster

**Key takeaways:**

* A TrainJob references a ClusterTrainingRuntime through `runtimeRef` instead of embedding per-job infrastructure
* `numNodes` and `resourcesPerNode` replace the v1 Master/Worker replica and per-replica resource configuration
* The `torch-distributed` and `training-hub` runtimes are cluster-scoped and provided by the platform

**Next steps:**

Now that you know what a runtime provides, launch your first distributed
PyTorch `TrainJob` from the CLI in the hands-on module.
