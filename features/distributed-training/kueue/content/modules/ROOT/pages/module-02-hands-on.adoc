= Module 02: Hands-on Exercise
:navtitle: Module 02: Hands-on Exercise

In this module you will work through the core Kueue workflow end to end: submit a
PyTorch training job to your LocalQueue, watch Kueue admit it, hold a second job that
exceeds the quota, and monitor Kueue health with alerts and error messages.

**Learning objectives:**

* Submit a training job to a LocalQueue with the `kueue.x-k8s.io/queue-name` label
* Read Workload resources to see how Kueue admits and holds queued work
* Use Kueue alerts and the documented error messages to troubleshoot queueing problems

== Exercise 1: Submit a queued training job

You submit workloads to a queue by creating them in a Kueue-managed project with the
`kueue.x-k8s.io/queue-name` label. Kueue creates a Workload resource for the job and
only lets the job's pods run when the quota is available.

First, create the training script. This example training script selects its backend
dynamically: `nccl` for GPU, `gloo` for CPU, so it runs on the CPU-only workshop
cluster. Save it as `train.py`:

[source,bash,role="execute"]
----
cat > train.py <<'EOF'
import os
import torch
import torch.distributed as dist

def main():
    # Select backend dynamically: nccl for GPU, gloo for CPU
    backend = "nccl" if torch.cuda.is_available() else "gloo"
    # Initialize the process group
    dist.init_process_group(backend)
    # Get rank and world size
    rank = dist.get_rank()
    world_size = dist.get_world_size()
    # Select device dynamically
    device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
    print(f"Running on rank {rank} out of {world_size} using {device} with backend {backend}.")
    # Initialize tensor on the selected device
    tensor = torch.zeros(1, device=device)
    if rank == 0:
        tensor += 1
        for i in range(1, world_size):
            dist.send(tensor, dst=i)
    else:
        dist.recv(tensor, src=0)
    print(f"Rank {rank}: Tensor value {tensor.item()} on {device}")

if __name__ == "__main__":
    main()
EOF
----

Create a ConfigMap to store the training script:

[source,bash,role="execute",subs="attributes"]
----
oc create configmap training-script-configmap --from-file=train.py -n {guid}-{user}
----

Create a file named `pytorchjob.yaml` that defines the training job:

[source,bash,role="execute"]
----
cat > pytorchjob.yaml <<'EOF'
apiVersion: kubeflow.org/v1
kind: PyTorchJob
metadata:
  name: pytorch-ddp
  labels:
    kueue.x-k8s.io/queue-name: workshop-lq
spec:
  pytorchReplicaSpecs:
    Master:
      replicas: 1
      restartPolicy: OnFailure
      template:
        metadata:
          labels:
            app: pytorch-ddp
        spec:
          containers:
          - name: pytorch
            image: registry.redhat.io/rhoai/odh-training-cuda128-torch28-py312-rhel9:v3.0
            command: ["python", "/workspace/train.py"]
            volumeMounts:
            - name: training-script-volume
              mountPath: /workspace
            resources:
              requests:
                cpu: "1"
                memory: 2Gi
              limits:
                cpu: "1"
                memory: 2Gi
          volumes:
          - name: training-script-volume
            configMap:
              name: training-script-configmap
    Worker:
      replicas: 1
      restartPolicy: OnFailure
      template:
        metadata:
          labels:
            app: pytorch-ddp
        spec:
          containers:
          - name: pytorch
            image: registry.redhat.io/rhoai/odh-training-cuda128-torch28-py312-rhel9:v3.0
            command: ["python", "/workspace/train.py"]
            volumeMounts:
            - name: training-script-volume
              mountPath: /workspace
            resources:
              requests:
                cpu: "1"
                memory: 2Gi
              limits:
                cpu: "1"
                memory: 2Gi
          volumes:
          - name: training-script-volume
            configMap:
              name: training-script-configmap
EOF
----

The `kueue.x-k8s.io/queue-name` label binds the job to the `workshop-lq`
LocalQueue, which queues it against the ClusterQueue quota. `replicas: 1` —
only one master node is needed for the PyTorchJob. The training image is the
RHOAI CUDA training image; the script still runs on CPU because it selects the
`gloo` backend when no GPU is present. The CPU and memory requests must fit
within the ClusterQueue nominal quota, or Kueue holds the job. The ConfigMap
mounts the training script that you created into the job pods.

[NOTE]
====
The example is configured for NVIDIA GPUs in the RHOAI documentation. If you use AMD
accelerators, change `nvidia.com/gpu` to `amd.com/gpu` in the resource requests and
remove any `NCCL_DEBUG` environment entries from the job manifest.
====

Create the distributed training job:

[source,bash,role="execute",subs="attributes"]
----
oc apply -f pytorchjob.yaml -n {guid}-{user}
----

=== Verify

Monitor the running distributed training job:

[source,bash,role="execute",subs="attributes"]
----
oc get pytorchjobs -n {guid}-{user}
----

The `pytorch-ddp` job is listed. Then check the pod logs:

[source,bash,role="execute",subs="attributes"]
----
oc logs <pod-name> -n {guid}-{user}
----

The logs show each rank's tensor value. In the console, click *Workloads* → *Pods*
and verify that the requested head pod and worker pods are running.

Your job ran through the queue. Now submit a second job that exceeds the quota to see
how Kueue holds work.

== Exercise 2: Watch Kueue make scheduling decisions

Kueue creates a Workload resource for every job that it manages. A Workload shows
whether the job is admitted, pending, or suspended, and why.

Create a file named `pytorchjob-xl.yaml` — a copy of `pytorchjob.yaml` with the name
`pytorch-ddp-xl` and resource requests that exceed the `workshop-cq` nominal quota of
8 CPU, for example `cpu: "50"` in both replica specs:

[source,bash,role="execute"]
----
sed -e 's/name: pytorch-ddp$/name: pytorch-ddp-xl/' \
    -e 's/cpu: "1"/cpu: "50"/' -e 's/memory: 2Gi/memory: 8Gi/' \
    pytorchjob.yaml > pytorchjob-xl.yaml
----

Apply the job:

[source,bash,role="execute",subs="attributes"]
----
oc apply -f pytorchjob-xl.yaml -n {guid}-{user}
----

List the Workloads:

[source,bash,role="execute",subs="attributes"]
----
oc get workloads -n {guid}-{user}
----

Expected output (abbreviated):

----
NAME                  QUEUE         ADMITTED   AGE
pytorch-ddp-2f4d7     workshop-lq   True       5m
pytorch-ddp-xl-9c1ab  workshop-lq   False      30s
----

The small job is admitted; the oversized job is not.

Diagnose why the oversized job is held from the console:

. In the {openshift_console_url}[OpenShift console], select your project from the Project list.
. Click *Search*, and from the Resources list, select *Workload*.
. Select the Workload resource that is created with the `pytorch-ddp-xl` job, and click the *YAML* tab.
. Check the text in the `status.conditions.message` field, which provides the reason for the pending state.

The message follows this pattern, reported in the RHOAI documentation for a GPU
shortage:

[source,yaml]
----
status:
  conditions:
  - lastTransitionTime: '2024-05-29T13:05:09Z'
    message: >-
      couldn't assign flavors to pod set small-group-jobtest12: insufficient quota
      for nvidia.com/gpu in flavor default-flavor in ClusterQueue
----

== Exercise 3: Monitor Kueue with alerts and error messages

Kueue ships alerting rules that each provide a link to a runbook with resolution
instructions.

In the OpenShift console, in the Administrator perspective:

. Click *Observe* → *Alerting*.
. Click the *Alerting rules* tab to view a list of alerting rules for default and user-defined projects.
. Click the name of an alerting rule to see the condition that triggers it. The following table summarizes the alerting rules for Kueue resources.

[cols="1,2,5",options="header"]
|===
|Severity
|Name
|Alert condition

|Critical
|KueuePodDown
|The Kueue pod is not ready for a period of 5 minutes.

|Info
|LowClusterQueueResourceUsage
|Resource usage in the cluster queue is below 20% of its nominal quota for more than 1 day. Resource usage refers to any resources listed in the cluster queue, such as CPU, memory, and so on.

|Info
|ResourceReservationExceedsQuota
|Resource reservation is 10 times the available quota in the cluster queue. Resource reservation refers to any resources listed in the cluster queue, such as CPU, memory, and so on.

|Info
|PendingWorkloadPods
|A pod has been in a Pending state for more than 3 days.
|===

If the Alert state of a rule is *Firing*, click *Observe* → *Alerting* and then the
*Alerts* tab, open each alert for the firing rule, and in the Runbook section follow
the linked runbook steps to identify the cause and resolve the situation.

When you troubleshoot queueing problems, these documented errors are the most common:

[options="header"]
|===
|Error message
|Cause
|Resolution

|`Default Local Queue with kueue.x-k8s.io/default-queue: true annotation not found please create a default Local Queue or provide the local_queue name in Cluster Configuration.`
|No default local queue is defined, and a local queue is not specified in the cluster configuration.
|In the console, select your project, click *Search*, and from the Resources list select *LocalQueue*. If a local queue exists, specify it in your configuration; if none exists, contact your administrator.

|`local_queue provided does not exist or is not in this namespace. Please provide the correct local_queue name in Cluster Configuration.`
|The specified local queue does not exist, or exists in a different namespace.
|Check the spelling of the local queue name and that the namespace in your configuration matches your project.

|`failed calling webhook "mraycluster.kb.io" ... no endpoints available for service "kueue-webhook-service"`
|The Kueue pod might not be running.
|Check `oc get pods -n redhat-ods-applications | grep kueue`, then contact your administrator.

|Workload pods terminated before the image was pulled
|Kueue waits 5 minutes by default before marking a workload as ready; a very large image that is still being pulled after that causes Kueue to fail the workload and terminate the pods.
|Check the pod *Events* tab to see whether the image pull completed, then contact your administrator.
|===

=== Verify

After you resolve the cause of any firing alert, the alerting rule stops firing.

== Clean up

Delete the training jobs and their workloads:

[source,bash,role="execute",subs="attributes"]
----
oc delete pytorchjob/pytorch-ddp -n {guid}-{user}
oc delete pytorchjob/pytorch-ddp-xl -n {guid}-{user}
----

Confirm that the Workloads are gone:

[source,bash,role="execute",subs="attributes"]
----
oc get workloads -n {guid}-{user}
----

== Module summary

**What you accomplished:**

* Submitted a PyTorch training job to your LocalQueue and watched its pods run
* Held a second job that exceeded the ClusterQueue quota and read the Workload conditions that explain why
* Reviewed the Kueue alerting rules and the documented queueing error messages

**Key takeaways:**

* The `kueue.x-k8s.io/queue-name` label routes a workload to a LocalQueue
* The Workload resource reports the admission decision, and its conditions explain held work
* Kueue alerting rules fire with runbook links when queues or controller pods misbehave
