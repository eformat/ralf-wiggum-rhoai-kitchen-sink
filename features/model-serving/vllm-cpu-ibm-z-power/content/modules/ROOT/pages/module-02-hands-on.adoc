= Module 02: Hands-on Exercise
:navtitle: Module 02: Hands-on Exercise

In this module you will work through the core vLLM CPU ServingRuntime workflow end to end:
verify the deployment from the CLI, access the authentication token and inference endpoint
for your deployed model, and send OpenAI-compatible inference requests to it.

**Learning objectives:**

* Verify a deployment from the CLI and confirm the model server pod is running
* Access the authentication token and inference endpoint for a deployed model
* Send OpenAI-compatible inference requests to the model with a bearer token

== Exercise 1: Verify the deployment from the CLI

The *Deploy a model* wizard from Module 01 creates a KServe `InferenceService` resource
in your working project. You can verify everything it created without leaving the terminal.

.Prerequisites

* You completed Module 01 and your model deployment shows a checkmark in the *Status*
column on the *Deployments* tab

.Procedure

. Confirm the `InferenceService` exists in your project:
+
[source,bash,role="execute",subs="attributes"]
----
oc get isvc
----
+
The output lists your model deployment with its URL and readiness state.

. Check the `Ready` condition of the inference service:
+
[source,bash,role="execute",subs="attributes"]
----
oc get isvc -o jsonpath='{.items[0].status.conditions[?(@.type=="Ready")].status}'
----
+
The output is `True` when the deployment is ready.

. Check that the model server pod is running:
+
[source,bash,role="execute",subs="attributes"]
----
oc get pods
----
+
The output includes a predictor pod named after your model deployment with a status of
`Running`.

. If you enabled *Model access* in the wizard, get the external route for your deployment:
+
[source,bash,role="execute",subs="attributes"]
----
oc get routes
----
+
If your project contains more than one route, pick the one named after your model
deployment. The host in the output matches the inference endpoint shown in the dashboard.

=== Verify

The `InferenceService` reports `Ready: True`, the predictor pod is `Running`, and the
route host matches the *Inference endpoints* value in the dashboard. If the pod is stuck
in `Pending` or `CrashLoopBackOff`, check the pod logs for model-loading or
resource-allocation errors and confirm your CPU and memory requests match the model size.

The deployment is healthy from the CLI's point of view. Next you talk to the model the
way real applications do — over the inference API.

== Exercise 2: Make authenticated inference requests

When you deploy a model by using the model serving platform, the model is available as a
service that you access using API requests. The vLLM runtime is compatible with the
OpenAI REST API, and the model serving platform uses the HTTPS port of your OpenShift
router (usually port 443) to serve external API requests.

.Prerequisites

* Your model deployment is ready (Exercise 1)
* You selected *Require token authentication* and entered a service account name in the
wizard in Module 01

.Procedure

. Retrieve the authentication token from the dashboard: click *Projects*, click the name
of your project, click the *Deployments* tab, and expand the section for your model. Your
token is shown in the *Token authentication* section, in the *Token secret* field. Click
the *Copy* button next to the token value and export it, replacing `<token-secret-value>`
with the value you copied:
+
[source,bash,role="execute",subs="attributes"]
----
export TOKEN=<token-secret-value>
----
+
Alternatively, retrieve the token from the CLI — the secret is named after the service
account you entered in the wizard in Module 01 (`{token_service_account}` if you used
the default):
+
[source,bash,role="execute",subs="attributes"]
----
export TOKEN=$(oc get secret {token_service_account} -o jsonpath='{.data.token}' | base64 -d)
----

. Get the inference endpoint. From the dashboard, click *AI hub*, *Deployments* — the
inference endpoint for the model is shown in the *Inference endpoints* field. From the
CLI, use the route host from Exercise 1:
+
[source,bash,role="execute",subs="attributes"]
----
export ENDPOINT_URL=$(oc get routes -o jsonpath='{.items[0].spec.host}')
----

. Confirm the runtime serves your model by listing the models behind the endpoint:
+
[source,bash,role="execute",subs="attributes"]
----
curl -v https://$ENDPOINT_URL:443/v1/models -H "Authorization: Bearer $TOKEN"
----
+
A successful response returns HTTP `200 OK` with JSON containing a `data` array; each
entry has `"object": "model"`, and the model `id` matches your model deployment name.

. Send a chat completion request to the model:
+
[source,bash,role="execute",subs="attributes"]
----
curl -v https://$ENDPOINT_URL:443/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{ "messages": [{ "role": "user", "content": "What is Red Hat OpenShift AI?" }] }' \
  -H "Authorization: Bearer $TOKEN"
----
+
A successful response returns HTTP `200 OK` with JSON containing a `choices` array; each
entry has a `message` with the text generated by your model in its `content` field.

[NOTE]
====
As of vLLM v0.5.5, you must provide a chat template while querying a model using the
`/v1/chat/completions` endpoint. If your model does not include a predefined chat
template, use the `--chat-template` command-line parameter in your custom vLLM runtime —
add it in the wizard under *Advanced settings* with *Add custom runtime arguments*:
+
[source,yaml]
----
containers:
- args:
- --chat-template=<CHAT_TEMPLATE>
----
+
Replace `<CHAT_TEMPLATE>` with the path to your template. You can use the chat templates
available as `.jinja` files or with the vLLM image under `/opt/app-root/template`.
====

. Verify that requests without a token are rejected:
+
[source,bash,role="execute",subs="attributes"]
----
curl -v https://$ENDPOINT_URL:443/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{ "messages": [{ "role": "user", "content": "What is Red Hat OpenShift AI?" }] }'
----
+
The request is rejected with an HTTP `401 Unauthorized` response, confirming that token
authentication protects your inference endpoint.

=== Verify

The `/v1/models` request lists your model, the chat completion request returns generated
text, and the unauthenticated request returns `401 Unauthorized`. If you receive `404` or
`503` errors, verify that the model status is ready before sending inference requests and
confirm that your bearer token has not expired.

You have now completed the core vLLM CPU ServingRuntime workflow on IBM Z / Power:
deployed a model on CPU-only nodes, verified it, and served authenticated inference
requests through the OpenAI-compatible API.

== Module summary

**What you accomplished:**

* Verified the deployment from the CLI: the `InferenceService` reports `Ready: True` and the predictor pod is `Running`
* Retrieved the authentication token and inference endpoint for the deployed model from the dashboard and the CLI
* Sent authenticated OpenAI-compatible requests to the `/v1/models` and `/v1/chat/completions` endpoints and confirmed unauthenticated requests are rejected with `401`

**Key takeaways:**

* The wizard deployment is a KServe `InferenceService` in your project — `oc get isvc` and the dashboard show the same state
* The vLLM runtime is compatible with the OpenAI REST API, served over the HTTPS port of the OpenShift router (usually port 443)
* Token authentication rejects unauthenticated requests with `401 Unauthorized`; the token is generated for the service account you chose in the wizard

**Next steps:**

Continue to the conclusion for the supporting documentation, or repeat the wizard
deployment in Module 01 with a different model or resource sizing to see how CPU-only
serving behaves on your IBM Z or IBM Power nodes.
